# 架构说明

这份文档解释 fde-kit 为什么长成这样。如果你只想跑起来，看 README 就够了。

## 一、一次问答的完整路径

```
问题
 │
 ├─ plan        去掉口语前缀；用本体匹配查询里的实体（型号/故障码/序列号）
 │
 ├─ retrieve    BM25 top-50  ┐
 │               向量 top-50  ┴→ RRF 融合 → 本体加权 → MMR 去重 → top-k
 │
 ├─ assemble    近重复剔除 → 句子级压缩 → 编号 [S1..] → token 预算截断 → 注入记忆
 │                                    │
 │                                    └─ 覆盖率闸门：不达标直接拒答
 │
 ├─ draft       有模型：按系统提示作答，强制每个结论带 [S#]
 │               无模型：抽取式，把最相关原文摘出来并标注来源
 │
 └─ verify     校验引用编号是否真实存在 → 计算置信度 → 无引用则重写一次
                最终落库：会话记忆 + 可选的评测记录
```

四个节点是纯函数，签名统一为 `state -> 状态增量`：

- `agent/nodes.py`：`plan / retrieve / draft / verify`
- `agent/agent.py`：串行引擎（默认，零依赖）
- `agent/graph_langgraph.py`：把同样的函数连成 `StateGraph`，支持条件重试边

这样做的好处很实际：CI 里跑串行版就够，装不装 langgraph 不影响正确性；装了也只是换个执行器。

## 二、数据模型

四张主表，全部在单文件 SQLite 里：

| 表 | 一行是什么 | 关键字段 |
|---|---|---|
| `assets` | 一份被纳入知识库的原始资料 | `sha256` 唯一，用于幂等重编译 |
| `chunks` | 一个可检索、可引用的证据单元 | `asset_id + ord` 定位，`section` 供引用展示 |
| `entities` | 一个本体抽取结果 | `chunk_id`、`normalized`（供查询侧匹配） |
| `vectors` | 一个分块的向量 | float32 BLOB，检索时整体载入内存 |

另有 `runs`（编译/评测运行记录）、`evals`（逐条结果）、`memory`（会话记忆）、`kv`（revision 等）。

**为什么用 SQLite 而不是 Postgres + pgvector？**
交付现场的第一性约束是“能不能在一台干净的笔记本上 30 秒跑起来”。
8000 分块以内，numpy 精确余弦比任何 ANN 索引都快且准。
真的超了，`retrieve/vector.py` 只有一个 `search(query_vec, k)` 接口，换实现不影响上层。

**为什么 `revision` 单调递增？**
检索器缓存（BM25 倒排、向量矩阵、字级集合）全部按 revision 失效。
编译完成后 `bump_revision()`，下一次检索自动重建。没有它就会出现“重新编译了但还在答旧内容”的经典 bug。

## 三、关键取舍

### 1. 中文为什么用 bigram，而不是分词

现场资料里大量型号、故障码、缩写，词典分词会把 `E021`、`SN-2024-0311` 切碎或切错。
bigram 不依赖词典、对新词天然鲁棒，代价是索引变大、有跨词噪声。
跨词噪声在**打分**上影响不大（BM25 的 idf 会自然压低高频 bigram），
但在**判别**上很致命——所以才有了字级的覆盖率指标（见下）。

### 2. 为什么两路融合用 RRF 而不是加权求和

BM25 的分数无上界、随文档长度与查询词数漂移；余弦在 [-1,1]。
两者相加必须先做分布校准，而校准参数每个客户都不一样。
RRF 只看名次，天然免校准，是现场最稳的默认值。要调权重，RRF 也支持 `weights`。

### 3. 拒答闸门为什么用 IDF 加权覆盖率

一开始试的是“BM25 分数低于阈值就拒答”，失败得很干脆：
RRF 把所有结果的分数压到 0.03 附近，而 BM25 原始分对短查询天然偏低。
换成**字级、IDF 加权、字词在语料中不存在则按 df=0 计最大 idf** 的覆盖率后，区分度非常干净：

| 问题 | 覆盖率 |
|---|---|
| A100 的整机保修期是多久 | 1.00 |
| 退货运费由谁承担 | 1.00 |
| E021 故障码怎么处理 | 0.63 |
| 这批设备出口欧盟的 CE 认证编号（库里没有） | 0.14 |
| 公司年会在哪里办（库外） | 0.00 |

阈值 0.35 在这份语料上把域内域外切得很开。**换语料必须重新标定**，所以它做成了环境变量。

### 4. 为什么置信度封顶

离线抽取式回答最高 0.75。不是谦虚：抽取式没有归纳能力，
它只能说“原文这么写”，不能说“所以结论是这样”。置信度如果给到 0.95，是在骗人。

### 5. 为什么编译失败也要留痕

`parse_pdf` 遇到损坏文件返回 warning 而不是抛异常。一次现场编译可能 3000 份文件，
坏一份不能全废；更重要的是，**失败清单本身就是交付物**——
报告里那句“这 6 份资料未纳入”，往往比任何技术指标都更能推动客户补齐材料。

## 四、扩展点

| 想做的事 | 改哪里 |
|---|---|
| 接新数据源（飞书/企微/数据库） | 实现 `ingest/base.py` 的 `Connector.iter_docs()` |
| 接新文件格式 | `compile/parse.py` 加一个 `_parse_xxx`，注册到 `parse_doc` 的映射 |
| 换向量库 | `retrieve/vector.py` 的 `VectorIndex` |
| 换 embedding / 模型 | 环境变量；`retrieve/embed.py`、`llm/client.py` |
| 加检索信号（图、规则） | `retrieve/hybrid.py` 里多一路 ranking，RRF 加一个权重 |
| 换切块策略 | `compile/chunk.py`；注意 `tabular=True` 时不要开重叠 |
| 改验收指标 | `eval/metrics.py`；新增指标记得同步 `summarize` 与报告 |

## 五、性能边界

示例语料（6 文档 / 24 分块）上，`ask` 端到端 6 ms，编译 0.2 s。
外推：1 万分块、单次查询约 30～60 ms（numpy 精确余弦 + 纯 Python BM25），
编译时间主要花在解析与 embedding 调用上。
真正的瓶颈从来不是检索，是 PDF 解析和模型调用。
